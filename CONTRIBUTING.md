# Contributing to the DROS Website

Conventions for anyone working in this repository. These are not stylistic
suggestions - breaking them has caused real bugs in this codebase before.

## Content Style

- **No em dashes.** Never use an em dash in page content, headings, labels,
  strings, or any user-visible text. Use a regular hyphen surrounded by spaces
  ( - ) instead.

## Shared Layout Components

- **The header and footer must be identical on every page.** Always use the
  shared `Navbar` component from `src/views/Navbar.tsx` and the shared `Footer`
  component from `src/views/Footer.tsx`.
- **Never inline a nav or footer.** Every new page must import and render
  `<Navbar />` and `<Footer />`. No exceptions.
- **To change nav or footer links or content**, edit only the shared component
  files (`Navbar.tsx` / `Footer.tsx`). Never patch them page by page.

## How Routing Works

Routing is **file-based** (Next App Router). A route exists because a directory
under `app/` contains a `page.tsx`. To add `/blogs/my-new-post`:

1. Write the UI as `src/views/BlogPostMyNewPost.tsx`.
2. Create `app/blogs/my-new-post/page.tsx`, which exports the route's `metadata`
   and renders that view:

```tsx
import type { Metadata } from 'next';
import BlogPostMyNewPost from '../../../src/views/BlogPostMyNewPost';

export const metadata: Metadata = {
  title: 'My New Post',
  description: '...',
  alternates: { canonical: '/blogs/my-new-post' },
};

export default function Page() {
  return <BlogPostMyNewPost />;
}
```

The sitemap is generated by `app/sitemap.ts` from the routes under `app/`, using
the hostname `https://dros.ai`, so a new `page.tsx` is picked up with no extra
step.

The old `export const route` declaration, `scripts/sync-routes.js`, and the
`npm run sync-routes` postinstall step are all gone. The filesystem is the single
source of truth now: a page without a `page.tsx` directory has no route, and
there is no scan to exclude layout pieces from.

## Adding a New Blog Post

1. **Create the view** at `src/views/BlogPostXxx.tsx`, using `export default
   function`, and build it with `BlogLayout` plus `<Navbar />` and `<Footer />`.
2. **Create the route** at `app/blogs/your-slug/page.tsx`, exporting `metadata`
   (including `alternates.canonical`) and rendering the view. See "How Routing
   Works" above for the shape.
3. **Add it to the listing** in `src/views/BlogsPage.tsx`: append an entry to the
   `blogPosts` array with `title`, `category`, `tags`, `summary`, `slug`,
   `readTime`, and `badge`. The `category` value must exactly match one of the
   values in the `categories` array at the top of that file.
4. **Verify the slug matches.** The `slug` in `BlogsPage.tsx` must be identical
   to the directory name under `app/blogs/`. A mismatch produces a post that is
   listed but links to a 404.
5. **Confirm the build passes** with `npm run build`.

## Before You Commit

```bash
npm run typecheck   # tsc, no emit
npm run lint        # eslint
npm run build       # must succeed
```

If you changed anything that renders, also run the visual gate against a
production build (`npm run build && npm run start` in another shell):

```bash
npm run parity      # every route, 3 viewports, must be 0 differing pixels
npm run parity:ssr  # every route must server-render its real content
```

`parity` diffs against `parity/baseline/`, captured from the pre-migration Vite
build. A deliberate visual change means the baseline is now wrong: re-capture it
with `npm run parity:capture` in the same commit, so the diff shows up in review
rather than being silently absorbed.
